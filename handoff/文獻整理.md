## 一、核心問題與建議主軸

### 1.1 瓶頸

- **功能上無法和 NotebookLM 區別**：手寫辨識、附出處的回答、限定資料範圍、閃卡與測驗，它都有。
- **「人是否看得懂」缺乏客觀的衡量方式。**

### 1.2 重新定義

區別不應該是「我們也做得到」，而是一個**可以被證明或推翻的主張**：

> **在不經使用者修正的情況下**，用專門工具拆解筆記、LLM 只負責讀內容、程式負責投票與驗證，能讓手寫繁中筆記的文字與結構辨識更準確，並讓根據辨識稿產生的答案更正確；以現成指標量測。辨識層和自己的基準（整頁 Gemini）比；**答案層**再以 NotebookLM 為對照組（它的辨識稿看不到，不能比辨識層）。

（原主張「能看到並修正 AI 讀到的內容，會讓使用者更能發現錯誤」已暫停。）

benchmark 本身就是區別：贏了，區別有數據支撐；沒贏，也是誠實的研究結論。

### 1.3 建議主軸

> **手寫筆記的結構忠實辨識與可驗證問答**
>
> 1. 把手寫筆記中的文字，以及箭頭、圖解等結構，轉成結構化資料（文字＋Mermaid 或節點連線清單）；多次獨立辨識由程式投票、結構由程式驗證，不合法就自動重新產生。
> 2. 用現成 benchmark 的指標客觀評分；NotebookLM 只在答案層當對照組。
> 3. 利用長上下文整份送出，評估重點放在「送進去的內容對不對」，而不是檢索。
> 4. 研究只量未經人工修正的輸出；逐步加入每個辨識改良做消融，量出各自的貢獻。（使用者實驗暫停。）
> 5. 訓練小模型列為延伸項目，先確認 Gemini 真的做不好再做。

## 二、與 NotebookLM 的區別

### 2.1 NotebookLM 目前已有的功能

| 功能 | 狀況 |
|---|---|
| 手寫筆記 | 可上傳圖片，App 內建相機，會做文字辨識（2025 年底加入） |
| 附出處的回答 | 只根據上傳資料回答，附出處 |
| 限定資料範圍 | 發問時可勾選要用的資料 |
| 閃卡、測驗 | 有，並記錄學習進度（2026 年 4 月更新） |
| 自動分類資料 | 有（2026 年 4 月加入），正是我們依設計原則取消的功能 |

### 2.2 不建議主張的點

「支援手寫」「附出處」「只根據筆記回答」「可以分類」「繁體中文」：它都有。「更準確」：沒有對照實驗前不能說。

### 2.3 可以主張的區別

| 區別 | 說明 | 狀態 |
|---|---|---|
| **不經修正的辨識與答案更準**（目前主張） | 專門工具拆解＋程式投票與驗證；尤其是箭頭、圖解等結構 | 待 R0 取得 NotebookLM 基準、G1 量測 |
| ~~看得到並能修正 AI 讀到的內容~~ | 產品功能保留，但不作為研究主張 | ⏸ 暫停 |
| **每一步可檢查、由規則決定** | 出處由伺服器核對；分類與範圍由使用者決定；拒答以字串判斷 | 已實作 |
| **能量化評估** | 辨識錯誤和自己的基準比；幻覺、出處正確率、拒答和 NotebookLM 比 | 待做 |
| **開放、可自行部署** | 程式碼公開、資料自己掌握、可換模型 | 已實作，對一般使用者吸引力較低 |

### 2.4 定位說法

> NotebookLM 是通用的資料研究工具；NoteHandler 專注在**手寫筆記的結構忠實辨識**：不需要使用者修正，就把手寫的文字與箭頭、圖解讀對，每個出處都經過程式核對，並且量化辨識正確率（和直接讀的基準比）與回答正確率（和 NotebookLM 比）。

## 三、現成的 benchmark 與指標

沒有現成 benchmark 剛好是「台灣高中手寫筆記問答」，但每個環節都有現成的**指標與評分方式**。做法是：**準備自己的小型測試資料，評分方法照既有論文**。

### 3.1 系統層級（不需要受試者）

| 要衡量的 | 現成 benchmark／指標 | 用法 |
|---|---|---|
| 手寫辨識 | **OmniDocBench**（CVPR 2025，中英文，含手寫筆記類）、**OCRBench v2**（含手寫內容擷取） | 用其指標（編輯距離、字元錯誤率 CER）評我們的辨識稿；可先跑其手寫子集驗證評分程式 |
| 模糊文件的辨識幻覺 | **KIE-HVQA**（NeurIPS 2025） | 參考其「看不清楚時是否硬猜」的評估方式 |
| 答案幻覺 | **RAGTruth**（ACL 2024，約 18,000 筆人工標註，標到詞的層級） | 照其幻覺分類與標註規範標註我們的回答 |
| 答案忠於資料 | **RAGAS Faithfulness**（有依據的主張數 ÷ 全部主張數） | 定義可照用；其預設用 LLM 評審，與設計原則衝突，建議改為人工標註 |
| 出處正確性 | **ALCE**（EMNLP 2023）：引用召回率、引用精確率 | 直接套用在〔來源〕上，補上「出處內容是否相符」的缺口 |
| 長上下文 vs RAG | **LaRA**（ICML 2025） | 參考其任務分類比較整份送出與檢索 |
| 箭頭、心智圖、流程圖 | **MindBench**（心智圖結構解析，中英雙語）、**FlowVQA**、**AI2D**、**SketchJudge**（手繪圖表） | 用其結構指標（節點、連線 F1）評估箭頭是否讀對 |

### 3.2 使用者層級：人是否看得懂

**不能用的量法：** 「你看得懂嗎？」問卷（主觀、易高估）；LLM 評審（違反設計原則）；只比答案正確率（量的是模型不是人）。

**前置材料：**
- 真實手寫筆記，每頁有人工校正的標準辨識稿（**不可放進公開 repo**）。
- 問題分三類：筆記有答案、需整合多頁、**筆記沒有答案**。每題有標準答案與頁碼。

**三個任務：**

| 任務 | 做法 | 指標 |
|---|---|---|
| 1. 判斷答案對錯（核心） | 受試者看系統回答，判斷是否符合筆記，可使用該系統所有介面；部分答案本來就錯，事先人工標好 | 錯誤發現率、**過度信任率**（錯的被判為對）、誤判率、d′、每題時間 |
| 2. 找出辨識錯誤 | 限時檢查 AI 讀到的內容，指出讀錯處 | 找到的錯誤數 ÷ 實際錯誤數、指出的錯誤中正確的比例 |
| 3. 理解測驗 | 使用後**關掉系統**做測驗；選擇、填空由程式對答案，申論由兩位不知條件的評分者依評分表打分（Cohen's κ ≥ 0.6） | 測驗分數（確認理解沒有變差） |

**實驗設計：**

| 條件 | 內容 |
|---|---|
| A | 只有答案（一般 RAG） |
| B | 答案＋可點的出處 |
| C | 答案＋出處＋原稿與辨識文字並排（完整 NoteHandler） |

- **主實驗在自己系統內做消融**，品牌與熟悉度相同，錯誤可以控制。
- 受試者內設計，筆記與條件以拉丁方陣輪替；受試者約 20–30 位，依預期效果重算檢定力；以 Wilcoxon 或混合效應模型分析。
- **對照實驗加入 NotebookLM**：錄下其真實回答再人工標錯；錯誤數量無法控制，指標用比例並說明限制。

**結果解讀：**

| 結果 | 代表 |
|---|---|
| C 的過度信任率明顯較低，理解分數沒有下降 | 區別成立 |
| C 發現較多錯誤，但時間多很多 | 有幫助但有成本 |
| 三條件沒有差別 | 原稿對照無幫助，主張需調整 |
| NotebookLM 錯誤本來就極少 | 手寫辨識對它不是問題，區別需轉向 |

## 四、長上下文 vs RAG

**結論：** 「給越多資訊越準」在「整份放得進、而且不算太長」時大致成立；越長越容易漏看或出錯，「幻覺會減少」目前沒有一致證據。

### 4.1 支持長上下文

| 論文 | 發表 | 發現 |
|---|---|---|
| Retrieval Augmented Generation or Long-Context LLMs? A Comprehensive Study and Hybrid Approach（Li 等，Google DeepMind） | EMNLP 2024 Industry | 資源足夠時，長上下文平均表現**一致**勝過 RAG；RAG 便宜很多。提出 Self-Route：先判斷檢索片段夠不夠，不夠才整份送 |
| Can Long-Context Language Models Subsume Retrieval, RAG, SQL, and More?（LOFT） | 2024 | 32k–1M token 範圍內，長上下文模型能媲美專門的檢索與 RAG 系統；組合推理仍弱 |
| Long Context vs. RAG for LLMs: An Evaluation and Revisits（Li, Cao, Ma, Sun） | 2025 | 問答任務長上下文普遍較好；摘要式檢索接近長上下文，**切塊檢索落後**；對話類 RAG 較好 |

### 4.2 反對或提出限制

| 論文 | 發表 | 發現 |
|---|---|---|
| Lost in the Middle（Liu 等） | TACL 2024 | 相關資訊在開頭或結尾表現最好，**在中間時明顯下降**；越長整體越差 |
| Context Length Alone Hurts LLM Performance Despite Perfect Retrieval | EMNLP 2025 Findings | 即使完整找到相關資訊，輸入變長仍使表現下降 **13.9%–85%**，且長度仍在模型宣稱上限內 |
| NoLiMa | ICML 2025 | 不能靠字面比對時，13 個宣稱支援 128K 的模型中 10 個在 32K 掉到短文本的一半以下；GPT-4o 從 99.3% 降到 69.7% |
| RULER | 2024 | 模型實際有效長度遠短於宣稱長度 |
| In Defense of RAG in the Era of Long-Context Language Models（NVIDIA） | 2024 | 提出 OP-RAG：片段**依原文順序**排列；片段數增加時品質呈倒 U 形，最佳點以更少 token 勝過整份送入 |
| LaRA — No Silver Bullet | ICML 2025 | 2,326 題、11 個模型；沒有萬用解。在**幻覺偵測**任務上，整份送入反而幻覺**更多** |

### 4.3 直接討論幻覺

| 論文 | 發現 |
|---|---|
| Not All Needles Are Found（2026） | 研究事實在長文中的分布與「不要編造」提示對幻覺風險的影響，與我們的提示詞設計直接相關 |
| MMLongCite（2025） | 評估視覺語言模型在長上下文下的引用忠實度，最接近「圖片筆記＋出處」 |
| FaithEval | 資料有雜訊或與常識衝突時，模型是否仍只根據資料回答 |

業界報告（非同儕審查）：Databricks「Long Context RAG Performance of LLMs」、Chroma「Context Rot」。

### 4.4 對專題的意義

1. **我們的做法與主流結論一致**：6 萬字元約 2 萬 token，在「放得進、不算太長」範圍內。NoLiMa 顯示多數模型在 32K 左右明顯退步，**上限不應無限制調高**。
2. **超過上限時的檢索已採用 OP-RAG 的關鍵做法**：片段依原順序排列並補回頁碼。
3. **不能直接主張「幻覺會減少」**。保險說法：「整份送入避免了檢索漏掉資料造成的錯誤，但長度本身也會帶來錯誤，所以我們限制長度，並用出處核對。」
4. **可做成實驗**：比較整份送入、切塊檢索、依原順序檢索三者的幻覺率與出處正確率（`WHOLE_CORPUS_CHARS=0` 可強制檢索）。

## 五、減少 LLM 參與能否降低幻覺

**結論：** 沒有研究直接證明「AI 用得越少，幻覺越少」，這句話本身也不一定成立。但有文獻支持四個更精確的說法。

### 5.1 有證據支持的說法

**(1) 把 LLM 限縮在擅長的部分，其餘交給固定程式，準確度較高**

| 論文 | 發現 |
|---|---|
| Less Is More: Measuring How LLM Involvement Affects Chatbot Accuracy in Static Analysis（ACM GPCE 2026） | **最直接的一篇**。把「交給 LLM 多少」當實驗變數：只產生有格式限制的 JSON＋固定程式轉換，比直接產生高 15–25 個百分點，也勝過多步驟呼叫工具 |
| PAL: Program-aided Language Models（ICML 2023） | LLM 只寫程式，計算交給 Python；比大很多的模型還準 |

限制：非筆記問答，量的是準確度而非幻覺。

**(2) 串連的 LLM 步驟越多，整體越容易出錯**

- 可靠度相乘（Lusser's Law）：每步 95%，串 10 步約剩 60%。
- 多篇 agent 研究觀察到錯誤累積。限制：多為業界文章與預印本，適合說明原理。
- 對應做法：回答只有「辨識 → 回答」兩步呼叫 LLM。

**(3) 模型的自我判斷與自我檢查不可靠**

| 論文 | 發現 |
|---|---|
| Large Language Models Cannot Self-Correct Reasoning Yet（ICLR 2024） | 無外部回饋時難以自我修正，有時修正後更差 |
| Large Language Models are not Fair Evaluators（2023） | LLM 評審有位置偏誤，調換順序就能改變排名 |
| Judging the Judges（IJCNLP 2025） | 15 個 LLM 評審、超過 15 萬次評估，確認偏誤非隨機 |

對應做法：不讓模型標「推測」；出處由程式比對；評量用人工標註。

**(4) 輸出越接近原文，幻覺越少，也越容易驗證**

| 論文 | 發現 |
|---|---|
| Copy-Paste to Mitigate Large Language Model Hallucinations（ICLR 2026） | 在 RAGTruth 上，複製原文程度與不忠實幻覺呈負相關 |
| The Extractive-Abstractive Spectrum（2024） | 越自由生成，使用者覺得越有用（最多 +200%），但正確引用句子比例最多下降 50%，驗證出處時間最多 3 倍 |
| On Faithfulness and Factuality in Abstractive Summarization（ACL 2020） | 摘要越偏離原文越不忠實 |

對應做法：提示詞要求保留原始用語，每個重點附出處；「驗證時間」可作為使用者實驗指標。

### 5.2 報告寫法

> 我們不主張「少用 AI 就少幻覺」，而是依據以下證據設計：
> 1. 把 LLM 限制在只有它能做的步驟，其餘交給固定程式（Less Is More, 2026；PAL, 2023）。
> 2. 減少串連的 LLM 呼叫，避免錯誤累積。
> 3. 不依賴模型的自我判斷（Huang et al., 2024；Wang et al., 2023）。
> 4. 讓回答貼近原文並附出處（Copy-Paste, 2026；Extractive-Abstractive Spectrum, 2024）。

### 5.3 反例

- 規則寫得差一樣會錯：例如空白頁判斷依賴模型寫的科目，只寫姓名的頁面沒被排除。
- LOFT 顯示有些情況交給 LLM 更好。
- 精確說法：「**可以用可驗證規則完成的步驟，就不要交給 LLM**」。

### 5.4 自己量

在系統上做消融：程式核對出處 vs LLM 判斷出處；使用者選類別 vs LLM 判斷類別。用 RAGTruth、ALCE 指標量化，把設計原則本身變成研究結果。

## 六、提升圖形辨識精準度的方法與工具

**原則：** 不讓一個模型一次包辦整張圖；先用專門工具拆解，再讓模型處理拆好的部分，最後用程式交叉檢查。

### 6.1 專門的文字辨識與版面分析工具

| 工具 | 特點 | 授權 |
|---|---|---|
| **PaddleOCR 3.0（PP-OCRv5）** | 支援繁中；官方稱對複雜中英文手寫明顯改進；小於 1 億參數，可本機執行 | Apache-2.0 |
| **PP-StructureV3** | 文件圖片轉 Markdown／JSON，官方稱在 OmniDocBench 表現最佳 | Apache-2.0 |
| **MinerU** | 版面、表格、公式，OmniDocBench 領先 | 開源 |
| **olmOCR** | 掃描文件，olmOCR-Bench 領先 | Apache-2.0 |
| **Mathpix** | 手寫公式業界標準 | 商用 |

不同 benchmark 排名互相矛盾，**必須用自己的筆記測試**。

### 6.2 裁切、放大局部

- **MLLMs Know Where to Look**（ICLR 2025）：模型準確度對目標大小非常敏感；模型知道該看哪裡但看不清楚。自動裁切後再問，不需訓練即可明顯提升。
- 用法：先切出區塊，逐塊放大送 Gemini。對小字、上下標、小箭頭有幫助。

### 6.3 把圖形轉成文字結構再推理（箭頭、流程圖）

| 論文 | 做法 | 結果 |
|---|---|---|
| TextFlow（NAACL 2025） | 先轉成 Mermaid／Graphviz，再根據文字回答 | FlowVQA、FlowLearn 最佳；錯誤可追溯到「看錯」或「推理錯」 |
| Arrow-Guided VLM（2025） | 先偵測節點與箭頭起訖點、再 OCR 節點文字，連同座標寫進提示詞 | 80% → 89%；「下一步」問題 100% |

限制：都是印刷流程圖，**手寫箭頭沒人測過**，是風險也是機會。

### 6.4 回傳座標框，逐行對齊原稿

- Gemini API 支援回傳座標框（`[y_min, x_min, y_max, x_max]`，0–1000 比例座標），可指定 JSON 格式。
- 用法：每行文字、每個箭頭附座標框；點辨識文字時在原稿標出對應區塊，從逐頁對齊進步到**逐行對齊**。
- 限制：座標框也是模型輸出，需搭配交叉檢查。

### 6.5 限制輸出格式並用程式驗證

- 以 JSON schema 或 Mermaid 語法規定輸出。
- 程式檢查：Mermaid 能否解析、箭頭是否指向存在的節點、座標框是否在圖片範圍內。
- 模型只產生，對錯由程式判斷，符合設計原則。

### 6.6 兩個獨立引擎交叉比對

- 同一區塊分別由 Gemini 與 PaddleOCR 辨識，程式比對：一致則可信度高；不一致則標出請使用者確認。
- 傳統 OCR 常用多引擎投票（如 Calamari）；「意見不一致時至少一個是錯的」也是偵測幻覺的常用信號。
- 與專題總覽的 I3 直接相關：不一致處由程式投票決定（研究不與使用者修正掛鉤，不再交給使用者確認），**不需模型自評**。

### 6.7 補充

- **影像前處理**：拉正、透視校正、提高對比（OpenCV），成本低，對手機照片有效。
- **Seeing is Believing?**（NeurIPS 2025）：提出 KIE-HVQA；訓練 7B 模型在看不清時拒答，無幻覺準確度比 GPT-4o 高約 28 個百分點。若之後要訓練小模型，這是最接近的參考。

### 6.8 建議的辨識流程

```
手機照片
  → ① 前處理（拉正、提高對比）                   OpenCV，固定程式
  → ② 版面分析，切出文字區、公式區、圖形區         PP-StructureV3 或 MinerU
  → ③ 每區裁切放大
       文字區：Gemini ＋ PaddleOCR 各讀一次 → 程式比對，不一致處標出
       圖形區：箭頭與節點偵測 → Gemini 產生 Mermaid ＋ 座標框 → 程式驗證語法與連線
  → ④ 組回整頁辨識稿，每行帶座標框
  → ⑤ 編輯器：點辨識文字 → 原稿標出對應區塊；待確認處以底色標出
```

LLM 只出現在第 ③ 步的「讀內容」；切割、比對、驗證、標記都是固定程式。

## 七、其他方向的可行性

| 方向 | 別人做了嗎 | 可行性 | 評估 |
|---|---|---|---|
| **手寫箭頭、圖解轉結構化資料** | MindBench、FlowVQA 做印刷或合成圖；**手寫、中文、筆記中的圖**幾乎無人做 | 高：先用 Gemini 產生 Mermaid，以 MindBench 指標評分 | **最推薦**，直接回應「結構轉成電腦能理解的資訊」 |
| **自動整理相關性與排版（設計 agent）** | NotebookLM 已有心智圖、自動分類 | 技術可行 | **不建議**：已有人做、違反設計原則、難客觀評分。若做，只畫出筆記原有結構 |
| **語言模型對齊（RLHF）** | 大量研究 | 低：需訓練大模型 | 不當主題；我們做的是「接地」（答案對得上筆記、出處對得上原稿） |
| **解決幻覺** | 大量研究 | 低 | 改為「量化＋讓使用者發現」 |
| **租算力訓練小模型** | — | 依任務 | **瓶頸是資料不是算力**。通用辨識不要自己訓練；窄任務才值得：例如箭頭偵測（LoRA 微調約 3B 視覺模型，需 24GB 以上顯卡，這時租算力才有意義）。順序：先做 Gemini 基準 → 標註資料 → 找出失敗處 → 只針對失敗處訓練 |
