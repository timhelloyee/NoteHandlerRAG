## 0. 讀這份文件前要先知道的

### 專題目標（排序判準）

**讓使用者用 NoteHandler 做出以科目別的筆記整理與查詢；判準是模型的輸出能不能讓使用者看懂自己的筆記內容。**

檢索排名等數值只是手段，不是目標。使用者在 2026-09 明確要求：不要過度強調數值高低，而忽略輸出是否讓使用者明白自己的筆記。

### 系統概要

- 使用者上傳手寫繁體中文筆記（圖片、PDF、文字檔），可選擇放進某個類別。Gemini 逐頁辨識成 Markdown，以 `intfloat/multilingual-e5-base` 嵌入後存進該類別的 Chroma。
- 問答：可選一個類別，或「全部類別」。送出的範圍在 `WHOLE_CORPUS_CHARS`（預設 60,000）以內時，**整份送進 Gemini，不走檢索**；超過才用檢索。
- 部署：後端在 HF Space（Docker，`https://timhelloyee-notehandler.hf.space`），前端由 Space 直接提供，另有 GitHub Pages 副本（`docs/index.html`，Pages 目前未啟用）。筆記存在私有 HF Dataset `timhelloyee/notehandler-store`，不進 git。
- 主要檔案：`app/rag_core.py`（約 1,350 行）、`app/main.py`（約 460 行）、`app/static/index.html`（約 1,250 行）、`app/static/ui_editor.html`（本機樣式編輯器）。

### 必須遵守的規則

| 規則 | 原因 |
|---|---|
| 用 `C:/Users/user/anaconda3/envs/ragtraining/python.exe`，不要用裸 `python` | 裸 `python` 沒有 torch |
| 在 PowerShell 跑測試前設 `$env:PYTHONIOENCODING="utf-8"` | 預設 cp950 會在輸出中文時崩潰 |
| 改完 `app/static/index.html` 一定要複製到 `docs/index.html` | Pages 用的是手動副本，兩份必須 byte-identical |
| 部署時 GitHub（`origin`）和 HF Space（`hf`）都要推 | 兩個是獨立的 remote |
| **後端和前端必須一起部署** | 新後端會拒絕舊前端的請求，新前端也無法搭配舊後端 |
| HF 推送由使用者在**自己的終端機、NoteHandler 資料夾內**執行 `git push hf main:main` | 背景執行無法跳出 Git Credential Manager 登入視窗；使用者家目錄本身也是 git repo，在錯的資料夾會找不到 `main` |
| 本機開發只用 `scripts/dev_server.py`（`.claude/launch.json` 已指向它），**不要**直接跑 `uvicorn app.main:app` | `.env` 含 `HF_TOKEN`，直接跑會還原並寫回真實的私有 Dataset。9/14 曾因上層資料夾的舊啟動設定發生一次（只有讀取），已修正 |
| 本機伺服器啟動後先看 `/api/health`：必須是 `disabled` | `ok` 代表連到了真實 Dataset，立刻停掉 |
| 不要放寬 `unavailable` 狀態下的寫入封鎖 | 同步現在會讓 Dataset 鏡像本機資料夾，筆記庫沒載入時寫入會刪掉雲端上的真實筆記 |
| 兩個 HF token 分開：Space secret 要能寫 **Dataset**；筆電 push token 只給 **Space** | 筆電 token 外洩時，不應連帶讓人能改寫筆記 |
| 絕不要求、顯示 token 值，也不要把 token 放進指令或 remote URL | 會留在 shell 歷史與 git 設定中 |
| **GitHub repo 與 HF Space 都是公開的** | 推到 `main` 的任何檔案都會公開 |
| 絕不把筆記內容、`vectorstores/`、`pdf/`、`.devstore/`、`eval/b0/pages*`、含 gold facts 的題組放進 git | 筆記是使用者的私人資料 |
| 量測用 Qwen3 時必須 `EMBED_DTYPE=float32` | fp16 下重跑結果不一致 |
| force-push 需要使用者明確同意 | 曾為清除個資而改寫過歷史 |

## 1. 決定方向的事

1. **真實使用者幾乎不會走到檢索，但離邊界很近。** `_whole_corpus` 比較的是**含重疊的 chunk 總長**：`pdf/` 六份筆記是 56,527 字元（上限的 94%），約再 4～5 頁手寫筆記就會改走檢索。分類上線後，問單一類別時比較的是**該類別**的長度，所以選了類別就更不容易超過上限。研究線已降為次要（第 6 節）。
2. **專題目標：「整理」已可用，「查詢可追溯」還沒有。** 使用者能自訂類別、拖曳分類、指定類別問問題（第 5 節）；但答案沒有出處，無法從答案回頭對照原稿（方向 B）。
3. **兩個信任問題已上線修正**（第 4 節）：只帶 email 就能讀取他人筆記；同步失敗時顯示「尚無筆記」。

## 4. ✅ 已上線：信任與資料安全（`25fbb94`）

### 4.1 由後端驗證使用者身分

- 前端把 Google ID token 放進 `Authorization: Bearer`；`main.current_user` 用 `google-auth` 驗證簽章、`aud`、到期時間與 `email_verified`。**所有端點都不接受 `user_id`。**
- 驗證結果快取到 token 到期；驗證失敗 401，連不到 Google 503。
- 原稿以 token 抓取後用 `blob:` URL 顯示；`/original` 加 `Vary: Authorization, X-Dev-User`；CORS 允許 `PUT`。
- token 約一小時到期：只在有效時還原登入，`auto_select` + One Tap 自動重新登入，401 時明確登出。
- 本機開發以 `X-Dev-User` 代替 Google；偵測到 `SPACE_ID` 時拒絕啟用。

### 4.2 同步失敗時讓使用者知道

`rag_core.sync_status()` 由 `/api/health` 回傳：

| 狀態 | 條件 | 行為 |
|---|---|---|
| `ok` | 已從 Dataset 還原 | 無橫幅 |
| `disabled` | 沒有 token，且不在 Space 上 | 灰色「本機模式」 |
| `unavailable` | 還原失敗，或在 Space 上卻沒有 token | 紅色橫幅；上傳、修改、刪除、移動、類別操作與問答一律 503 |
| `unsaved` | 還原成功但之後某次同步失敗 | 黃色橫幅；下一次寫入即修復 |

### 4.3 原稿先存再同步

`_add_described_note` 先存原稿再同步，失敗時刪掉原稿，不留孤兒檔。

### 4.4 UI 樣式編輯器（僅本機開發模式）

`/ui-editor`：17 個設計變數與 3 個字型位置；只改寫 `:root` 並同步到 `docs/`；值以白名單驗證；Space 上 404。

## 5. ✅ 已上線：分類系統（`de82b07`）

### 5.1 使用者看到的

- **筆記分類**區塊：輸入名稱「新增類別」；每個類別標題列有「重新命名」「刪除類別」與筆數。
- 每筆筆記左邊的 ⠿ 可**拖曳**到其他類別；手機（HTML 拖放不可用）用每筆的「移到」選單。
- **刪除類別不會刪除筆記**：裡面的筆記先移到「未分類」。
- **問題範圍**選單：「全部類別」或某一個類別，下方說明文字會隨選擇改變。
- **放入類別**選單：上傳時決定筆記進哪個類別，預設「未分類」。

### 5.2 儲存方式

```
<VECTORSTORE_ROOT>/<使用者>/                     未分類（原本的筆記庫，舊資料不需搬移）
<VECTORSTORE_ROOT>/<使用者>/categories/<id>/     一個類別
    category.json                                {"name": ..., "created": ...}
    chroma.sqlite3、<Chroma 索引資料夾>、originals/
```

- **每個類別是獨立的資料夾**，各自有 Chroma 筆記庫與原檔。類別之間互不相依，也**無法建立子類別**（名稱不可含 `/`、`\`）。資料夾內仍有 Chroma 自己的索引子資料夾與 `originals/`，那是儲存格式，不是子類別。
- 資料夾以固定 id（`c` + 12 位十六進位）命名，**重新命名只改 `category.json`**，不必搬動 Chroma 開著的資料夾。
- 名稱規則：1–30 字、同一使用者內不分大小寫不可重複（409）、「未分類／全部／全部類別」為保留名稱。
- 筆記 id（檔名）在同一使用者的**所有類別間唯一**；開啟、編輯、移動、刪除只需要 id，伺服器自己找到所在類別。

### 5.3 行為保證

| 保證 | 做法 |
|---|---|
| **選了類別就只讀那個類別** | `rag_query(category=...)` 只打開該資料夾；整份模式與檢索模式都一樣。只有未選類別時才讀所有資料夾 |
| 移動不重新嵌入、不呼叫 Gemini | `_transfer_note` 直接複製向量、文件與 metadata，並搬移原檔；先寫入目的地再刪來源 |
| 編輯後留在原類別 | `update_note` 以原類別重建 |
| 不存在的類別不會被建立 | 上傳、問答、移動、刪除遇到未知 id 一律 404，並在呼叫 Gemini 之前檢查 |
| 使用者之間不共享類別 | 類別在使用者資料夾之下 |
| Windows 本機可刪除類別 | Chroma 會開著 SQLite；刪除前回收物件、清除 Chroma 快取並短暫重試（Linux 上的 Space 不受影響） |
| 刪掉的類別不會在重啟後回來 | `_persist_user` 改用 `upload_folder(..., delete_patterns="*")`，Dataset 鏡像使用者資料夾 |

## 6. 研究線學到了什麼（✅ 已降為次要，不再投入）

數字以修正題組後為準（29 題、62 頁、float32）。程式碼與數據保留，可作為報告的一節。

| 發現 | 證據 |
|---|---|
| 換嵌入模型是最大的槓桿 | e5 → Qwen3-0.6B，基準組 chunk MRR 0.799 → 0.871（差 +0.071，95% CI −0.017～+0.158）。未達顯著 |
| 保留結構測不出效果 | 結構切塊相對基準：e5 +0.001、Qwen3 +0.027；Holm 校正後無一成立 |
| 正對照沒有通過 | 刪除祖先路徑：e5 +0.052、Qwen3 −0.023，方向不一致 |
| 三個缺陷改變了結論 | 切塊器碎片、chunk 長度混淆、6 題洩題（修正後正負號翻轉） |
| MDE 太大 | n=29 下約 +0.07～+0.13 |

生產環境的 `STRUCTURED_RULE`、`chunk_by_structure`、`merge_target` 是死碼。

答案層級的新研究設計由另一個 AI 在 `研究流程 修改5.md` 與其審查回覆中進行，不在本 repo；作者已決定**不做干擾頁實驗**（使用者不會在自己的筆記中加入無意義內容）。

### 7.1 接著：把專題目標做完整

#### A. 自動建議科目（◐ 手動分類已上線；約 1 天）

- **已完成：** 使用者自訂類別、拖曳分類、指定類別問答（第 5 節）。
- **還缺：** 辨識出的科目完全沒被使用。每次上傳都要使用者自己選類別。
- **證據：**
  - 辨識提示詞第 1 條要求模型寫出科目，`rag_core.subject_of()` 能讀出來，但只存在文字裡。
  - `describe_pdf` 取**第一頁**的科目當整份筆記的科目：實測生物筆記的封面被判為「無科目」，整份被標錯；地科只寫姓名的 4 頁被標成「國文」。
- **做法：**
  - 以頁層級**多數決**取代「第一頁」，排除空白頁與不在 11 科清單內的值。
  - 上傳後，若有與科目**同名的類別**，在結果中建議「放進『生物』？」，由使用者一鍵確認；**不自動移動**（類別是使用者的，科目只是建議）。
  - 純文字筆記不經 Gemini，不做建議。
- **完成的樣子：** 上傳一份生物 PDF 到「未分類」，結果顯示「建議放進：生物」，按一下就移過去。

#### B. 答案附上出處（1–2 天）

- **證據：** `QueryResponse` 只有 `{answer, model}`；參考資料以 `"\n---\n".join(docs)` 串接，沒有檔名，模型無從引用。
- **做法：**
  - 每份筆記前加來源標頭（檔名），保留既有 `## 第 N 頁`。整份模式與檢索模式都要加。
  - 提示詞（`PROMPT_TEMPLATE`）要求每個重點標註來源。
  - 後端解析引用、剔除不存在的檔名或頁碼，回傳 `sources: [{id, page}]`。
  - 前端顯示可點的來源標籤，開啟既有的並排編輯器（`openEditor`）並用 `goto(page)` 跳頁。來源筆記可能在任何類別，編輯器只需要 id。
- **完成的樣子：** 每個答案都能一鍵回到原稿；引用到不存在頁碼的內容不會顯示。

#### C. 未選類別且超過上限時的處理（◐ 半天）

- **已完成：** 使用者選了類別時，整份模式的上限只看該類別，較不容易被迫改走檢索。
- **還缺：** 使用者選「全部類別」且總量超過 60,000 字元時，仍直接改走檢索（目前語料已達 94%）。
- **做法（二擇一，需作者決定）：**
  - 提示使用者「筆記太多，請選一個類別以得到更完整的回答」，仍照常以檢索作答。
  - 或從問題判斷最相關的類別，只送該類別整份（需要驗證判斷準確度）。

### 7.2 之後：幫使用者看懂自己的筆記

#### D. 標出模型沒把握的地方（約 1 天）

- **證據：** 人工校正發現 Gemini 在程式設計筆記中寫出原稿沒有的內容。提示詞第 4 條已要求標「（無法辨識）」，但介面沒有凸顯；推測內容沒有標記。
- **做法：** 沿用「（無法辨識）」並另加推測標記；編輯器以底色標出並提供「下一處」跳轉；清單顯示待確認數量。

#### E. 「筆記裡沒有」成為明確狀態（約半天）

- **證據：** 拒答字串「參考資料中沒有記載相關訊息」與一般短答案長得一樣。分類上線後更常見：在錯的類別問問題就會得到它。
- **做法：** API 回傳 `status`（`answered` / `not_in_notes`）；介面用不同樣式，並建議**改選其他類別或「全部類別」**再問。

#### F. 替舊筆記補上原檔（低優先，需要時再做）

- 缺原檔的 `lv.0_compressed.pdf` 已刪除，造成的 bug 已修好。又出現缺原檔、含手動修正的筆記時再做：只保存檔案並同步，不重新辨識。

#### G. 評量改成量「看不看得懂」（1–2 天，最好在 B 之後）

- 逐題檢查答案是否正確、引用是否指向正確頁、是否出現筆記裡沒有的內容、該拒答時有沒有拒答。詳細設計見外部的研究流程文件。

#### H. 類別統整與複習（視範圍，需先完成 B）

- 每個類別提供「產生統整」與「產生小測驗」，內容附來源，可用「儲存 .md」匯出。分類上線後可以直接以類別為單位做。

## 9. 暫停不做

| 項目 | 理由 |
|---|---|
| 版面偵測與結構保留實驗（B0、B4、M1–M3） | 優化的是使用者走不到的路徑，而且正對照沒有通過 |
| ColPali（B7）與 contextual retrieval（B5） | 同上；4.3 GB 顯示卡跑不動 ColPali |
| 干擾頁（合成語料規模）實驗 | 作者決定：使用者不會刻意在自己的筆記中加入無意義內容 |
| 現在就把線上嵌入模型換成 Qwen3 | 只影響檢索路徑；需重新嵌入所有類別的筆記並重新校準門檻 |
| 用 PDF.js 取代瀏覽器內建 PDF 檢視器 | 試過，同樣會閃白；目前的新 iframe 方案已解決 |
| 自動把筆記移進類別 | 類別屬於使用者；自動判斷只做建議（A） |
