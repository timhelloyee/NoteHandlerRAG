## 壹、審查所依據的實測資料

### 系統與語料

NoteHandler 是一套針對手寫繁體中文筆記的多模態 RAG 系統。審查用的語料為 `pdf/` 下六科共 66 頁（程式設計 lv.0、公民、地科、歷史、生物、物理），兩個組態都非空白的頁面共 **62 頁**。題組為 `eval/chunk_cases.json`，**29 題**（19 題 `fact`、10 題 `hierarchy`），每題的正解 span 都經人工確認只出現在單一頁的正文中。

### 三個組態（與原計畫定義相同）

| 代號 | 攝取方式 | chunk 數 |
|---|---|---|
| `B1` | Gemini 純文字 → 450 字滑動視窗（重疊 50） | 161 |
| `B4` | 巢狀 Markdown → 依標題層級切塊 ＋ 祖先路徑前綴 | 301 |
| `B0` | 人工校正文字 ＋ 人工結構樹 | 300 |

### 兩個嵌入模型

| 代號 | 模型 | 維度 |
|---|---|---|
| `E1` | `intfloat/multilingual-e5-base` | 768 |
| `E2` | `Qwen/Qwen3-Embedding-0.6B` | 1024 |

### 兩個評分單位（**這個區分在原文件中缺席，但它決定結論的正負號**）

- **chunk level**：第一個「內含正解 span」的 chunk 的排名。組態無關（各組態切塊邊界不同，所以 gold 是文字不是 chunk id）。**這是唯一有解析度的單位。**
- **page level**：第一個屬於正解頁的 chunk 的排名。小語料下會飽和。

### 重現指令

```bash
# 基線
python eval/gating_experiment.py

# 候選嵌入模型（float32 是必要的，見第伍節）
EMBED_DTYPE=float32 EMBED_MODEL=Qwen/Qwen3-Embedding-0.6B python eval/gating_experiment.py

# 跨嵌入模型的配對 bootstrap（不載入任何模型）
python eval/compare_runs.py intfloat_multilingual-e5-base Qwen_Qwen3-Embedding-0.6B

# 門檻校準
EMBED_DTYPE=float32 EMBED_MODEL=<hf-id> python eval/calibrate_gate.py
```

語料是磁碟快取的 JSON（`eval/corpus/corpus_b{0,1,4}.json`），重跑**不花任何 API 額度**。逐題排名存於 `eval/runs/<model>.json`，所以任何指標都可以事後重算而不必重跑檢索。

## 貳、修改 1：主指標

### 原判斷

> 單一 gold 的情況下 Recall@10 只有兩種值：0 或 1，區分度極低。改用 nDCG@10 ＋ MRR@10 作為主指標。

### 實測

前半段**成立**。chunk level 的 Recall@3 已經是 0.93（E1/B1）到 0.97（E1/B4），Recall@10 更加飽和。降級 Recall 是對的。

後半段**冗餘**。單一 gold ＋ 二元相關度時：

```
nDCG@10 = 1 / log2(rank + 1)        （IDCG = 1）
MRR@10  = 1 / rank
```

兩者都是 rank 的單調遞減函數，因此**逐題差值必定同號**。實測所有配對比較（3 組態 × 2 嵌入模型 × 2 單位）：

```
per-probe sign disagreements: 0/87 (E1, chunk)   0/87 (E1, page)
                              0/87 (E2, chunk)   0/87 (E2, page)
```

W/L 計數相同、符號檢定相同、bootstrap CI 幾乎相同。**兩者承載同一份資訊。**

### 判定

⚠️ 採納降級 Recall 的部分。但不要把 nDCG@10 與 MRR@10 並列為「兩個主指標」，那會讓讀者以為有兩個獨立讀數。

### 該怎麼改

- 主指標寫 **MRR@10**（對排名最敏感）。
- **同時報告 nDCG@10，理由寫明是「與 ViDoRe／ColPali 系列可比」** —— 這個理由本身充分且正確，不需要假借解析度。
- **不要對兩者分別做顯著性檢定**，那是同一個檢定做兩次。
- 原文件說「重算即可，不用重跑檢索，排名資料應該都還在」：**正確且已驗證**。本審查的 nDCG 欄位就是從 `eval/runs/*.json` 直接重算的，沒有重跑檢索。

## 肆、修改 3：決策門檻 —— 必須重寫

**這是本次審查最重要的一節。**

### 原判斷

```
Δ_oracle = B0 − B1              結構的總價值
Δ_llm    = B4 − B1              LLM 已取回的部分
R        = (B0 − B4) / Δ_oracle 幾何法可爭取的剩餘比例
```

| 條件 | 判定 | 路線 |
|---|---|---|
| Δ_oracle 的 95% CI 包含 0 | 結構不顯著 | 擴充資料集後重跑 |
| Δ_oracle 顯著 > 0 且 R ≥ 0.4 | 幾何法有空間 | 主線：開發版面偵測 |
| Δ_oracle 顯著 > 0 且 R < 0.4 | 模型推論已足夠 | 轉向：H3 |

### 實測

從逐題排名直接計算（`eval/runs/*.json`，10,000 次配對 bootstrap）：

| 嵌入模型 | 單位 | 指標 | B1 | B4 | B0 | **Δ_oracle** | Δ_llm | **R** | **R 的 95% CI** |
|---|---|---|---|---|---|---|---|---|---|
| e5 | chunk | MRR@10 | 0.813 | 0.783 | 0.738 | **−0.075** | −0.030 | +0.595 | **[−3.37, +5.23]** |
| e5 | chunk | nDCG@10 | 0.852 | 0.838 | 0.786 | **−0.067** | −0.014 | +0.786 | **[−3.70, +6.01]** |
| e5 | page | MRR@10 | 0.865 | 0.882 | 0.915 | **+0.050** | +0.017 | +0.655 | **[−2.08, +3.35]** |
| e5 | page | nDCG@10 | 0.890 | 0.912 | 0.936 | **+0.046** | +0.022 | +0.524 | **[−1.87, +2.77]** |
| Qwen3 | chunk | MRR@10 | 0.897 | 0.852 | 0.766 | **−0.131** | −0.045 | +0.657 | **[−0.32, +2.80]** |
| Qwen3 | chunk | nDCG@10 | 0.922 | 0.889 | 0.814 | **−0.108** | −0.034 | +0.688 | **[−0.23, +2.58]** |
| Qwen3 | page | MRR@10 | 0.897 | 0.891 | 0.859 | **−0.037** | −0.006 | +0.846 | **[−5.50, +6.00]** |
| Qwen3 | page | nDCG@10 | 0.922 | 0.918 | 0.895 | **−0.027** | −0.004 | +0.842 | **[−6.86, +7.42]** |

補充：Qwen3 chunk level 的 `B0 − B1 = −0.131`，**95% CI [−0.268, −0.006]，不含 0**。這是本專案唯一達到顯著的比較，方向是「B1 優於 B0」。

### 三個獨立的缺陷

**缺陷一：規則對已觀測到的結果無定義。**

判定表只有「CI 包含 0」與「顯著 > 0」兩個分支。實測 8 格中有 6 格的 `Δ_oracle` 是**負的**，其中一格顯著為負。**沒有任何一條規則能分類這個結果。**

**缺陷二：R 在分子分母同時為負時仍然「看起來正常」，因而會做出災難性的判定。**

八格的 R 全部落在 **+0.52 ～ +0.85**，全部 **≥ 0.4**。依規則，八格全部判定為「幾何法有空間 → 主線：開發版面偵測」——包括那六格「人工完美結構比現行系統更差」的情形。

> **這條規則會用一個負負得正的比值，授權七週的版面偵測開發。**

**缺陷三：R 是分母的 CI 跨越 0 的比值估計量（Fieller 問題），在 n=29 下不可估計。**

上表最右欄的 bootstrap CI 寬約 ±3 到 ±7。R 的點估計 0.657 與門檻 0.4 的比較，在統計上等同擲硬幣。原文件〈參〉附帶條件說「若 R 落在 0.3–0.5 的模糊地帶就不要硬做決定」——方向正確，但模糊地帶的實際寬度是 ±3，也就是**整條數線**。

**額外問題：規則沒有指定評分單位。**

e5 之下，`Δ_oracle` 在 chunk level 是 **−0.075**、在 page level 是 **+0.050**——**正負號相反**。一條會因為未言明的選擇而翻轉結論的規則，不算事先寫死。

### 該怎麼改

1. **保留事先寫死門檻的作法。這是整份文件最好的想法，不要因為公式有問題就放棄。**
2. **指定單位**：主判定用 **chunk level**（page level 已飽和，八格中的 page CI 全部含 0）。
3. **改用絕對差值與其 CI，做三向符號分支**，取代比值：

| 條件（chunk level, MRR@10, 配對 bootstrap 10,000 次） | 判定 | 路線 |
|---|---|---|
| `Δ_oracle` CI **完全 < 0** | **結構保真度與可檢索性衝突** | 轉向：以 H3 與「保真 vs 可檢索」的取捨為主軸 |
| `Δ_oracle` CI **含 0** | 結構不顯著 | 擴充資料集後重跑；同時報告可偵測的最小效果量 |
| `Δ_oracle` CI **完全 > 0** 且 `Δ_oracle − Δ_llm` 的 CI 完全 > 0 | 幾何法有空間 | 主線：開發版面偵測 |
| `Δ_oracle` CI 完全 > 0 但 `Δ_oracle − Δ_llm` CI 含 0 | 模型推論已足夠 | 轉向：H3 |

   第三、四列用 `Δ_oracle − Δ_llm`（＝ `B0 − B4`）的 **CI**，而不是比值。它是一個差值，CI 行為正常，且問的是同一個問題：「扣掉 LLM 已經取回的，還剩多少可爭取」。
4. **R 若要保留，只作為描述性數字報告，並且必須附上它的 bootstrap CI**，讓讀者看見它不可用。不要拿它當判定依據。
5. 依實測，**第一列（CI 完全 < 0）是目前最可能的結果**。這條路線的內容要事先寫好，不能等看到數字再想。

## 伍、修改 6：嵌入模型軸 —— 採納，並提高優先序

（先講這一項，因為它同時是修改 3 與修改 5 的前提。）

### 原判斷

> 論文 1 量到「換嵌入模型的增益常常大於換切塊策略的增益」。加做 2×3 穩健性檢驗。**成本很低——只要重跑嵌入與索引，不用重做任何標註，也不用改切塊程式碼。**

### 實測

**論文 1 的主張在你們自己的語料上成立，而且差距很大。**

| 變動的軸 | chunk level MRR 變化 |
|---|---|
| 換嵌入模型（e5 → Qwen3-0.6B，B1 不變） | **+0.083**　95% CI [−0.009, +0.175]，9W/2L |
| 換切塊策略（B1 → B4，e5 不變） | −0.030　95% CI [−0.149, +0.084] |
| 換切塊策略（B1 → B4，Qwen3 不變） | −0.045　95% CI [−0.163, +0.075] |

完整結果：

| 組態 | 嵌入模型 | chunk R@1 | chunk MRR | page MRR |
|---|---|---|---|---|
| B1 | e5 | 0.69 | 0.813 | 0.865 |
| **B1** | **Qwen3** | **0.83** | **0.897** | **0.897** |
| B4 | e5 | 0.62 | 0.783 | 0.882 |
| B4 | Qwen3 | 0.76 | 0.852 | 0.891 |
| B0 | e5 | 0.62 | 0.738 | 0.915 |
| B0 | Qwen3 | 0.66 | 0.766 | 0.859 |

**+0.083 的 CI 仍然擦到 0，不可稱為顯著**（符號檢定 9W/2L，p≈0.065）。正確說法是：*方向一致、是本專案至今最大的效果、但在 n=29 下未達分離*。**不要升級為「顯著」。**

分離度的改善是實打實的：無關繁中詞對的餘弦從 ~0.79 降到 ~0.31；問題與正解段落之間相對於最近錯誤段落的平均邊際從 **0.101 → 0.498**。

**組態之間的排序不變**（chunk level 兩個嵌入模型下都是 B1 ≥ B4 > B0），所以「保真 vs 可檢索」的發現**不是弱嵌入模型造成的假象**。

### 但是「成本很低」低估了三個坑

這三個都是實作時真的踩到的：

1. **所有原始距離常數屬於嵌入模型，不屬於系統。**
   e5 校準出的 `RELEVANCE_CEILING = 0.38`，**低於 Qwen3 最小的真實答案距離 0.408**。直接換模型而不重新校準，系統會**對每一個問題都回答「沒有記載相關訊息」，而且看起來一切正常**。
   實測分離度：

   | 嵌入模型 | 有答案（n=29）min/中位/max | 無答案（n=8）min/中位/max | 最佳單一切點 |
   |---|---|---|---|
   | e5 | 0.211 / 0.285 / 0.372 | 0.283 / 0.387 / 0.418 | 0.341 → 收 28/29、拒 5/8 |
   | Qwen3 | 0.408 / 0.662 / 1.125 | 0.830 / 1.169 / 1.368 | 1.003 → 收 28/29、拒 **6/8** |

   **兩個模型下有答案與無答案的分布都重疊**，不存在完美切點。這也代表拒答路徑是系統最弱的一環。
   工具：`eval/calibrate_gate.py`。每模型的值存在 `rag_core._GATE_BY_MODEL`。

2. **提示前綴是模型的一部分，不是裝飾。**

   ```
   e5     文件："passage: " + text     查詢："query: " + text
   Qwen3  文件：text（無前綴）          查詢："Instruct: {task}\nQuery: " + text
   ```

   餵錯家族的格式會**靜默地**降低檢索品質，不會報錯。

3. **Qwen3 在 fp16 下不具重跑再現性。**
   在 RTX 3050 上，兩次完全相同的 fp16 執行對 `cs-argv` 給出不同結果（第 1 名 ↔ 掉出 top-10），相當於 0.035 MRR。已排除 HNSW：與 numpy 精確搜尋逐題比對 **29/29 完全一致**。float32 則跨執行位元相同。
   **所有量測用的執行必須設 `EMBED_DTYPE=float32`。**

### 另外兩點

- 原文件用 Qwen3-0.6B（CMTEB 66.33）對比 **multilingual-e5-large-instruct**（62.0）。但 NoteHandler 實際跑的是 **e5-base**，更弱。**實際落差比引文所暗示的更大。**（66.33／62.0 這兩個數字本次未查證，引用前請回原始出處核對。）
- 2×3 的成本確實低：本次全部重跑都用磁碟快取語料，**零 API 花費**。但要加上上述三項前置工作，約半天到一天。

### 判定

✅ 採納，並建議**從「穩健性檢驗」提升為主要結果之一**。實測顯示你們沒有在變動的那個軸，效果比正在變動的軸大。

## 陸、修改 5：B5 contextual retrieval 與 B3 規格

### B5 本身

✅ **採納。** 定位論述寫得很好：

> 祖先路徑注入是 contextual retrieval 的確定性、零推論成本版本——脈絡不是被生成的，而是從版面結構中被讀出的。

成本可行：每個 chunk 一次 LLM 呼叫。62 頁約 161 chunks；擴到 300 頁約 800–1,200 次呼叫，以雙金鑰 fail-over 可行。

**但要事先準備好一個結果**：實測 B4（LLM 產生的 Markdown ＋ 祖先路徑前綴）**沒有**贏過 B1（−0.030 ／ −0.045）。M2 本質上是「換一棵更好的樹的 B4」。因此「M2 只能證明有注入比沒注入好」這個前提，其對應的實測代理目前是負的。**最可能的結果是 M2 ≈ M1 ≈ B5 全部打平**，這與論文 1 的預測一致。計畫要能容納這個結果並仍然有話可說（見第捌節）。

### B3 採用 RSC 門檻 —— 有技術錯誤

```
Tchunk 1,500 字元 · Tfinal 2,500 字元 · Tmerge 350 字元 · δ = 3
```

中文的字元數約等於 token 數。**`multilingual-e5-base` 的輸入上限是 512 token。** `rag_core.py` 的 `CHUNK_CHARS = 450` 正是為此而設。

因此在 `E1 = e5` 之下，1,500–2,500 字元的中文 chunk 會**超出輸入視窗 3–5 倍並被靜默截斷**——B3 量到的會是截斷行為，不是語意切塊。

> 這與本專案上週踩到的 `RELEVANCE_CEILING` 是同一類錯誤：**把屬於某個模型／某個語言的常數，當成管線的性質搬用。**

**該怎麼改**：依嵌入模型的實際上下文視窗換算後再寫進規格，並在文件中寫明換算依據。注意這與修改 6 交互作用——`E2 = Qwen3-Embedding` 的上下文是 32k，原始數字在該模型下沒問題。所以 B3 的規格必須**分模型寫**。

### 順帶：M1 的小 chunk 合併規則

✅ 採納，理由充分（`一下地科三段` p07–p10 之類只有一個姓名的頁面確實存在）。對應的消融項（`M2 − 小 chunk 合併`）也該加，理由寫得對：不加的話，評審可以主張增益其實只是 chunk 長度分布變得比較均勻。

### 策略層面

✅ **同意這是整份文件收益最高的一項。** 兩種結果都可寫，論證結構完整。〈額外收穫〉那段（注音問題是任何檢索路線都繞不過的，不是文字管線特有缺陷）尤其精準，確實把 Hand-off 2 從附帶功能提升為獨立研究缺口。

### 但成本估計錯誤

### 兩項原文件遺漏的整合成本

1. **B7 無法沿用現有的 Chroma 評測管線。** Late interaction 每頁存 ~1,030 個 128 維向量，用 MaxSim 計分，不是單向量 ANN。需要自寫計分器（66 頁規模下 numpy 幾行就好，但**是新程式碼，不是換 checkpoint**）。
2. **B7 只能在 page level 評分**，因為它回傳的是頁面不是 span。**你們唯一有解析度的 chunk level 對它不適用。** 而 page level 已經飽和：Qwen3 之下 B1 的 page MRR 是 0.897，本專案所有 page level 的 CI 都含 0。

   → **B7 只有在「ColPali 明顯較差」時才會產生可分辨的結果。** 這恰好是原文件預期且希望的結果，所以可以接受——但要寫進計畫，而不是跑完才發現。

## 捌、修改 7：流程圖

### 邏輯矛盾

```mermaid
F1 --> G1
F2 --> G1
F1 --> G2
F2 --> G2
G1[方法實作<br/>NSG · 版面偵測 · 結構切塊] --> H1
```

決策點一的兩條分支（`F1` 主線、`F2` 轉向）**都連到同一個 `G1`，而 `G1` 內含「版面偵測」**——正是 `R < 0.4` 那條分支決定不要做的模組。**如圖所示，決策沒有任何後果。**

`H1[主實驗 B0-B5,B7 對比 M1-M3]` 加深了這個問題：兩條分支下 M1–M3 都存在。

**該怎麼改**：`F2`（轉向）應連到一個**不含版面偵測**的節點，例如 `G1b[方法實作（轉向版）<br/>NSG 子樹切塊 · 穩定性量測 · 可稽核性]`，且該分支下的主實驗組別要對應縮減。

### 語法

其餘 Mermaid 語法可解析。建議把菱形標籤加引號以策安全：

```mermaid
E{"結構是否值得保留？<br/>Δ_oracle 與 Δ_oracle − Δ_llm 的 95% CI"}
```

未加引號的 `{}` 內含 `/` 與 `-` 是常見的 Mermaid 破圖來源。（標籤內容也應依第肆節改掉 R。）

## 拾壹、B0 不是「oracle 上限」

計畫大量依賴 B0 作為「結構價值的上限」。實測**這個命名在本語料上不成立**：

- chunk level：`B0 − B1 = −0.131`，**95% CI [−0.268, −0.006]，不含 0**。這是全專案唯一顯著的比較，方向是 B1 較優。
- 機制（已查證）：人工校正**移除了** Gemini 自行加上的標題與贅述，留下更精簡、詞彙表面更少的 chunk。**保真度與可檢索性相互衝突。**

原文件〈拾壹〉第 2 點說目的 1-4（oracle 上限）是計畫最好的部分之一——**同意，但框架要改**。從「結構價值的上限」改成「**保真度與可檢索性的取捨**」。後者是更有意思的結果，而且是你們自己量出來的，不是引來的。

（原文件提到論文 1 在 Limitations 明說缺少 chunk 層級 ground truth、論文 2 提到生成式切分輸出不一致——「別人只寫在限制章節的事，你們把它做成正式對照實驗」這個論點成立且有力，保留。）
